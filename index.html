Evolution Log Skill

An AI workflow for maintaining an EvolutionLog.md that explains how a system changes over time and why. It builds the narrative from Git history, PRDs, RFCs, and post-mortems, organizing each change around the problem, options considered, decision, result, and what came next.

Because the narrative is generated from multiple sources, the workflow also verifies commits and file references against the repository before updating the log.

What I’m exploring

Why I’m building this

Some thoughts behind what I’ve been building and what I’ve learned along the way.

What changes when AI becomes an engineering collaborator rather than just a coding tool?

Most AI coding tools focus on helping us write code faster. I’m interested in exploring a broader question: can agents participate across the software development lifecycle — understanding requirements, reviewing architecture, implementing changes, maintaining quality, and preserving knowledge as the system evolves?

The projects above are experiments around this question. While building them, a few ideas have become increasingly important to me.

Planning matters more than code generation

Many important engineering decisions happen before implementation starts. Requirements need to be clarified, assumptions challenged, architecture reviewed, and trade-offs understood.

That’s why I started by building agents around feature planning and architecture review rather than focusing only on code generation. If an agent can implement quickly but starts from the wrong assumptions or design, writing code faster doesn’t help much.

Documentation should evolve with the codebase

Documentation becomes outdated easily when maintaining it is separate from the development workflow.

I’m exploring whether agents can help maintain living documentation that evolves alongside the codebase — capturing not only what the system looks like today, but also why decisions were made, how the architecture changed, and what we learned along the way.

Evaluation is an engineering problem

As I gave agents more responsibility, I found that generating an output was only part of the problem. I also needed a reliable way to determine whether that output was actually correct and stayed within the intended scope.

That’s why the skills I build include verification mechanisms such as rubric-based evaluation, scope enforcement, and phantom commit audits. I see evaluation and guardrails as part of the system design itself: if an agent is going to participate meaningfully in engineering work, its output needs to be verifiable.
